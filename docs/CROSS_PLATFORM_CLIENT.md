# Cross-Platform Client Port

## What this is

The original client (`goat-client.exe`, `src/client/main.cpp`, 2,834 lines) is the entire playable game — every screen, the duel board, the shop, the deck editor — and it's pure Win32: GDI for all drawing, WIC for JPEG/PNG decode, a native `EDIT` control for text input, `CreateProcessW`/pipes to talk to the duel engine, and `std::wstring`/UTF-16 throughout. None of that exists on macOS/Linux, and there's no incremental "add an `#ifdef`" path — GDI/WIC/Win32 controls have no cross-platform equivalent at all.

This document tracks a **from-scratch port** of that client onto [raylib](https://www.raylib.com/) as a **new, separate target** (`goat-client-rl`, `src/client_rl/`) that builds alongside the original without touching it.

This is the largest task in the project by a wide margin — it took many sessions of work, not one. This file exists so any session (or any person) can pick it up without re-deriving the plan from scratch.

**Decision — `goat-client-rl` is now the primary client.** It reached full feature parity (every screen, including the duel board and engine IPC) and has had real duel-hang bugs found and fixed through actual play-testing (see "Bugs fixed" below) — enough to call it passable. `goat-client` (Win32/GDI) still exists and still builds on Windows, but it's a legacy build now: no further feature work, README/launcher point at `goat-client-rl` first. See the README's own "Cross-platform client" section for the user-facing version of this.

## Current status

**All ten screens exist and every Hub entry point is wired to a real destination** — Title, Hub, Collection, Shop, Pack Opening, Deck Editor, Deck List, CPU Select, and now the **duel board** (`Screen::Duel`), reachable from both PLAY CPU and TEST DUEL via CPU Select, plus AUTO DUEL as a synchronous Hub-only smoke test. Every screen but Duel shares one `draw_app_header` for the persistent "PROJECT GOAT" brand bar (the duel board deliberately doesn't — see below, matching the Win32 original). The engine IPC bridge (spawning `goat-sim`, the `request.txt`/`response.txt`/`state.txt` file protocol) is fully implemented, including a real cross-platform process-spawn abstraction (`src/client_rl/ProcessBridge.{hpp,cpp}`) rather than a Windows-only stopgap.

**Update — since played through for real:** a real duel was played and reported hanging on "Waiting for the rules engine…" indefinitely, at first seemingly at random. A follow-up, more specific report ("happens right after Set-ing a card," "happens throughout the opponent's turn") pinpointed the actual root cause: this toolchain's `fs::last_write_time()` truncates to ~1-second granularity, so `poll_player_duel`'s prompt-freshness check silently and permanently dropped any prompt published within the same wall-clock second as the previous one — not rare, close to guaranteed given how fast back-to-back decisions happen. See "Bugs fixed" below — this is the one fix in this whole file verified against a standalone reproduction of the *exact* reported failure (not just reasoned about): a test replicating the old algorithm reproduced the hang on demand (1 prompt, then a 60s timeout), and one replicating the new algorithm answered all 156 prompts of a full duel with zero delay between them.

The ~9-branch click-priority logic in `resolve_duel_click`, the zone-highlight legality logic, the hand popup, and the inspector's board-selection buttons are ported line-for-line from `handle_duel_click`/`paint_duel` and the core request/response cycle now has strong standalone-reproduction evidence behind it, but none of this has been confirmed by actually clicking through a duel in the running app — only via headless drivers hitting the same files. What has been verified independent of live play: the port compiles clean with zero warnings under `-Wall -Wextra`; the app launches and stays alive; `scripts/test-player-ipc.ps1` drives a full duel to completion via the raw protocol; and the standalone reproduction described above.

**Remaining:** full UTF-8 migration (already the pattern for every screen including Duel, so this is essentially done in practice — no `wstring` exists anywhere in `src/client_rl/`), the 3-OS CI build matrix, and visual polish. See "Remaining phases" below.

**Bugs fixed:**
- `goat-client-rl` crashed at startup (`open cards.cdb: out of memory` from SQLite) when launched from anywhere other than the repo root — e.g. double-clicked from `build/` — because every asset/data path in this client is relative and nothing changed the working directory first. Fixed by porting `src/client/main.cpp`'s `project_root()`/`SetCurrentDirectoryW` startup step (`main()` now calls `fs::current_path(project_root())` before constructing `AppState`). Verified by launching the built exe from both the repo root and `build/`.
- No card/pack art ever rendered (only the title screen's `.png` background did) — raylib's vendored `external/raylib/src/config.h` has `SUPPORT_FILEFORMAT_JPG` **disabled by default** (only PNG/BMP/TGA/GIF/QOI are on), and every card image (`external/card_images/*.jpg`), pack art (`external/packart/*.jpg`), and the card back (`external/extra/card_back.jpg`) in this project is a `.jpg`. `LoadImage()` on any of them silently failed (an "IMAGE: Data format not supported" warning, `image.data == nullptr`, no crash since `TextureCache`/`get_card_texture` already null-check). Fixed in `scripts/build-client-rl.sh`, which now builds raylib with `CUSTOM_CFLAGS="-DSUPPORT_FILEFORMAT_JPG=1"`. **Anyone with a stale `external/raylib/src/libraylib.a` built before this fix needs to `make -C external/raylib/src clean` once** (or just delete that file) so the next `build-client-rl.sh` run rebuilds raylib itself with the flag — the script only rebuilds raylib when the `.a` is missing. Verified with a standalone `LoadImage` smoke test against the rebuilt library (a sample card and a sample pack image both decoded with non-null data), plus the usual launch-and-stay-alive check.

**Bug found (not fixed — lives in `goat-client`, which this project treats as untouched):** while porting Pack Opening, `src/client/main.cpp`'s own `opening_reveal_tick` field is set on every pack purchase but never actually read anywhere — the WM_TIMER handler repaints the PackOpening screen but never advances `opening_revealed`, and the click handler only lets you *select* already-revealed cards, never reveal new ones. So in the shipped Win32 client, REVEAL ALL is the only way to ever see a card's face — the intended one-at-a-time flip animation the UI (and the "Skip the animation" subtitle) implies is currently unreachable. `goat-client-rl`'s Pack Opening screen implements the animation as evidently intended (using `GetTime()` each frame rather than a timer callback), so this is fixed here, just not backported to `goat-client`.

**Bug found (not fixed — same status as above):** `src/client/main.cpp`'s `load_next_player_deck` unconditionally overwrites `state.status` with `"Loaded " + <filename>` immediately after calling `open_deck_editor`, even on that call's failure path (which itself sets a more specific `"Cannot open deck: ..."` message into `status` first). So if a file in `decks/player/` becomes unreadable, LOAD's status line always claims success regardless. Low-stakes (only reachable if a saved deck file is corrupted/deleted out from under the app) — ported as-is for parity in `goat-client-rl` rather than silently "fixed," since it's such a narrow edge case that diverging from the original here didn't seem worth doing without being asked.

- A real duel could hang on "Waiting for the rules engine…" indefinitely, reported after actual play-testing. First pass:
  - **`submit_action`'s response write had no retry.** It writes `response.tmp` then renames it to `response.txt`, but the rename's `std::error_code` was captured and never checked. A transient rename failure — this project's own history already documents antivirus scan-locking on rapid temp-file-rename patterns as a real, observed cause in this exact sandbox — silently dropped the player's response while the client cleared the prompt as if it had sent it, leaving the engine's `choose_menu` polling for a `response.txt` that was never written (up to its own 60-second timeout). Fixed by retrying once after clearing the destination first, mirroring the engine's own `write_board_state` rename-fallback in `src/main.cpp`.
  - **Polling ran every single frame** (~60Hz) instead of throttled like the Win32 client's WM_TIMER (150ms, ~6.7Hz) — a deliberate simplification when the duel board was first built, reasoning the cheap early-outs in `poll_player_duel`/`poll_board_snapshot` made it harmless. That's ~9x more filesystem opens per second than the original ever produced, increasing exposure to exactly the kind of rename contention above. Throttled back to a 150ms interval (`paint_duel`'s `kPollIntervalSeconds`, via a new `last_poll_time` field) to match.
  - A **safety net independent of the root cause**: if the "waiting" gap exceeds 20 seconds (`kStuckDuelSeconds`), the prompt panel escalates its message and a click terminates the stuck duel process and returns to the Hub, rather than leaving zero recourse if something else causes a stall.

  **Follow-up deep audit** (requested after the first pass, to make sure this wasn't still happening intermittently) found and fixed one more concrete issue, plus made the safety net smarter:
  - **Every duel used the same fixed session directory** (`sessions/active-duel`, matching `src/client/main.cpp`'s own fixed name) regardless of which process was running it. A stray leftover `goat-client-rl.exe` instance — observed more than once in this project's own development, including earlier in this session (a leftover process held a file lock that blocked a rebuild) — writing to that same directory at the same time as the "real" instance would corrupt the IPC exchange in exactly the way that looks like a hung duel: a response vanishes, or a request meant for the other process's session gets picked up instead. Fixed with `goat::process::current_pid()` (new in `ProcessBridge`) — `session_directory` is now `sessions/active-duel-<pid>`, unique per running instance, so this class of interference is now structurally impossible rather than just unlikely.
  - **The stuck-detection fallback couldn't tell "busy" from "stuck."** A duel legitimately deep in a long CPU turn or a multi-link chain can go 20+ seconds without needing a decision from the human player at all, which would previously escalate to the same "may be stuck, click to abandon" message as a genuinely hung engine — a false alarm that could tempt someone into abandoning a perfectly healthy duel. Now tracks `last_board_change_time` (updated whenever `poll_board_snapshot` sees `state.txt` actually change) alongside `waiting_since`, and only escalates to the abandonable "Stuck" state (`DuelWaitState`) when *neither* a new prompt *nor* any board change has happened for the full window — a duel that's merely slow (state.txt still updating) now shows a distinct "still working" message instead, with no abandon option.
  - Verified: clean rebuild with zero warnings under `-Wall -Wextra`; `scripts/test-player-ipc.ps1` still passes; a standalone check confirmed `current_pid()` returns a distinct value per process. **Still not independently verified against the original reported symptom** — I can't reproduce the hang interactively, so this audit is "closed every gap found on careful re-reading," not "confirmed fixed against a repro." Worth another real play-through, ideally a longer one that exercises several chains/CPU turns.

  **Root cause, found on a second, more targeted report** ("setting a facedown card hangs it," "anytime it's the opponent's turn it happens too" — specific enough to point at *the moment right after any action*, not a rare timing accident): `poll_player_duel` detected a fresh `request.txt` via `fs::last_write_time()`. **This MinGW/libstdc++ toolchain's implementation of that function truncates to ~1-second granularity** — confirmed directly (a small standalone test rewrote a file 7 times, 5ms apart, and 6 of the 7 writes reported the *exact same* timestamp). Any second prompt published within the same wall-clock second as the previous one was therefore **silently and permanently dropped** — not a rare race, a near-guaranteed failure, since back-to-back decisions with effectively zero delay between them (right after Set-ing a card, or any CPU-turn response) are routine, not exceptional. This fully explains both symptoms in the report without needing to invoke timing luck at all.

  Fixed by dropping filesystem timestamps entirely for this purpose. `poll_player_duel` now tracks two timestamp-free signals instead: `request_txt_seen_missing` (the engine always deletes `request.txt` before it can ever publish a new one, so "have we observed the file absent since the prompt we last parsed" is a reliable freshness signal on its own) and `last_request_text` (a content comparison, as a second signal covering the one remaining edge case — a poll landing exactly in the sub-100ms gap between the engine deleting the old file and publishing an identical-text new one, missing the transient "absent" moment). `last_request_write_time`/`fs::file_time_type` are gone from `AppState` entirely.

  **Verified directly, not just built:** two standalone programs, both driving a real `goat-sim` duel with zero delay between decisions (worst case for same-second collisions) —
  - One replicating the **old** algorithm answered exactly **1 prompt** and then timed out after 60+ seconds, reproducing the reported hang on demand.
  - One replicating the **new** algorithm answered all **156 prompts** of a complete duel to a final result, with no delay between any of them.

  This is the strongest confidence level of any fix in this file so far — the exact reported failure mode was reproduced standalone, root-caused to a specific toolchain behavior, and the fix was proven against that same reproduction rather than just reasoned about.

- **`scripts/update-dependencies.ps1` would print scary, misleading "fatal: reference is not a tree" errors on any fresh checkout** — found while building `.github/workflows/release.yml` (its first-ever exercise of a genuinely fresh checkout; every local dev session up to this point already had every `external/` directory in some already-fetched state, so this never surfaced before). `BabelCDB`, `LFLists`, and the trimmed `CardScripts` subset are committed directly into this project's own git history rather than vendored as separate pinned clones, so on a fresh checkout their directories already exist (with the correct, already-complete files) but with no nested `.git` of their own. The script's existence check (`if (-not (Test-Path $target)) { git clone ... }`) only skipped the *clone*, not the unconditional `git -C $target fetch`/`checkout --detach` calls that followed it — and `git -C <path>` on a path with no `.git` of its own doesn't fail outright, it silently walks up and operates on *this project's own* `.git` instead (fetching this repo's own `origin`, then failing to check out the dependency's pinned hash, since that commit obviously isn't in this repo's object database). Verified empirically end-to-end before concluding this was safe-but-noisy rather than actually broken: an isolated sandbox repro confirmed a failed `git -C` checkout leaves the wrongly-targeted repo's `HEAD`/state completely untouched (no corruption risk), and a direct PowerShell test confirmed `$ErrorActionPreference = 'Stop'` does *not* halt the script on a plain native-command failure (only on `2>&1`-wrapped ones) — so the script was continuing on to fetch `raylib` correctly regardless, just with confusing noise for 3 of 6 dependencies along the way. Fixed by checking for `<dependency>/.git` specifically and skipping cleanly with an explanatory message when a dependency's content is already present via this repo's own tracking rather than a separate clone. Verified: re-ran the fixed script locally — the three already-committed dependencies now skip cleanly, `raylib`'s real fetch/checkout still succeeds, and a full rebuild afterward still works.

- **CI failed identically on all three platforms with `CMake Error ... No SOURCES given to target: ygopro_lua`**, reported directly from a real Actions run of `.github/workflows/release.yml`. Root cause: `external/ygopro-core` vendors `lua/src` as a git submodule (per its own `.gitmodules`, pointing at `https://github.com/lua/lua/`) — a plain `git clone` never fetches submodule content, so `lua/src` was left completely empty, and `CMakeLists.txt`'s `file(GLOB ... lua/src/*.c)` silently turned zero files into zero sources for that target. This was invisible in every local dev session up to now for the same class of reason as the entry just above it: this machine's `external/ygopro-core` had been sitting around since before this script's clone path was ever really exercised end-to-end, already carrying a properly-initialized `lua/src` from whenever it was originally set up — so `update-dependencies.ps1` had genuinely never performed a real fresh clone-and-checkout of this specific dependency until this bug was chased down. Fixed by adding `git -C $target submodule update --init --recursive` right after the `checkout --detach` line, applied unconditionally to every dependency in the loop (a harmless no-op for the ones with no `.gitmodules`, e.g. `raylib` — confirmed directly, `git submodule status` against it reports nothing) rather than special-casing `ygopro-core`. **Verified with a genuinely fresh, end-to-end run, not just an isolated reproduction**: backed up and deleted the local `external/ygopro-core` entirely, ran the real (fixed) `update-dependencies.ps1` from a clean slate, confirmed `lua/src` went from 0 files to the expected 35 `.c` files, then did a full clean CMake configure + build of `goat-client-rl` and `goat-sim` from that fresh checkout (`ygopro_lua` now resolves real sources, all 85 build steps succeed), ran the `goat-sim` smoke duel to completion, and launched `goat-client-rl` and confirmed it stays alive before killing it and cleaning up every test artifact.

- **Windows release packaging failed with `cp: cannot stat '/c/msys64/mingw64/bin/libgcc_s_seh-1.dll': No such file or directory`**, reported from a real Actions run — macOS and Linux both passed on that same run. The "Assemble release package" step hardcoded `/c/msys64/mingw64/bin/$dll` to find the MinGW runtime DLLs (`libgcc_s_seh-1.dll`, `libwinpthread-1.dll`, `libsqlite3-0.dll`, `libstdc++-6.dll`) `goat-client-rl.exe`/`goat-sim.exe` need bundled alongside them, but that path is only where MSYS2 happens to live on this local dev machine — `msys2/setup-msys2` installs under `${{ runner.temp }}` on GitHub-hosted runners, not a fixed `C:\msys64`, so the hardcoded path never existed there. The workflow's own smoke-test step already sidesteps this correctly by running through `shell: msys2 {0}` instead of plain `bash`, since the msys2 shell's `/mingw64/bin` always resolves correctly regardless of the real Windows-side install root — the packaging step just hadn't followed the same pattern. Fixed by splitting DLL-copying into its own step (`Copy MinGW runtime DLLs (Windows)`) that runs via `shell: msys2 {0}` and copies from `/mingw64/bin/$dll`, between the OS-agnostic "Assemble release package" step (now just binaries + data, no DLLs on Windows) and a new "Create release archive" step (the 7z/zip logic, unchanged). Verified `objdump -p` against a locally-built `goat-client-rl.exe` confirms it's genuinely dynamically linked against exactly those DLL names (not statically linked, so this bundling step is load-bearing, not defensive); the YAML was also validated to parse correctly after the restructure. Not yet confirmed against a real Actions run — worth a `workflow_dispatch` test run before the next real tag.

## Architecture decisions (already made — don't re-litigate without a reason)

- **Toolkit: raylib.** Compared against SDL2+SDL_ttf+SDL_image, Dear ImGui, and Qt/GTK/wxWidgets: the existing code is **immediate-mode** — every screen is a plain function that draws rectangles/text/bitmaps fresh every frame and does its own manual rect-based mouse hit-testing. raylib's `DrawRectangleRec`/`DrawTextEx`/`DrawTexturePro` + per-frame `GetMousePosition()`/`IsMouseButtonReleased()` polling is a near 1:1 conceptual match. It's also one dependency (window + input + 2D drawing + JPEG/PNG decode all built in) instead of three, which matters once there's a 3-OS CI matrix to keep in sync. Retained-mode widget toolkits would mean a full architectural rewrite on top of the porting work, not just a rendering-backend swap.
- **New parallel target, not a rewrite of `goat-client`.** `CMakeLists.txt` has a `goat-client-rl` target (unguarded by `if(WIN32)`) alongside the existing `goat-client`. `src/client/Layout.hpp` (pure geometry, no Windows dependency except one `RECT`-returning method) was copied to `src/client_rl/Layout.hpp` with that one method dropped — otherwise identical.
- **raylib is vendored, not fetched via CMake `FetchContent`.** It's pinned in `scripts/update-dependencies.ps1` exactly like the project's other five external dependencies (git clone + pinned commit), and gitignored (`/external/raylib/`) — not committed, same as `ygopro-core`/`windbot`. This was a deliberate change from the original plan (which said FetchContent) once it became clear CMake itself doesn't run in this sandbox at all (see below) — vendoring the same way as everything else avoids having two different "how does this project get its dependencies" stories.
- **One `button(font, rect, title, subtitle, scale, mouse, clicked) -> bool` call both draws a button and reports whether it was just clicked.** This is a real simplification over the Win32 client, which needs a separate `compute_*_layout` / `paint_*` / `handle_*_click` trio for everything because GDI's message loop delivers paint and click as separate, decoupled events (`WM_PAINT` vs `WM_LBUTTONUP`). raylib's per-frame loop doesn't have that split. Keep using this pattern for every future screen rather than reintroducing the three-function split.

## Critical environment gotcha: two different toolchains

This project has been built, this whole session, with a devkitPro-bundled MSYS2 GCC that is **Cygwin-hosted** (`g++ -dumpmachine` → `x86_64-pc-cygwin`, defines `__CYGWIN__` but *not* `_WIN32`). That's fine for `goat-client`'s raw Win32 API calls (GDI doesn't care about `_WIN32` vs `__CYGWIN__`), but **raylib's GLFW backend gates its actual Windows implementation behind `_WIN32` specifically**. Under the Cygwin-hosted compiler, GLFW's `win32_*.c` files compile as empty stubs and linking fails with dozens of undefined `_glfwPlatform*` references. Forcing `-D_WIN32` gets further but then hits missing MinGW-only headers (`direct.h` etc.) that a genuine Cygwin CRT doesn't have.

**The fix:** build `goat-client-rl` and raylib with a genuine MinGW-w64 GCC instead (`-dumpmachine` → `x86_64-w64-mingw32`). One was found already installed on this machine at `C:\msys64` (a separate MSYS2 install from the devkitPro-bundled one), with a working `mingw64` subsystem. Like the devkitPro toolchain, it only resolves correctly when invoked via **its own** `usr/bin/bash.exe --login` (puts `/mingw64/bin` on `PATH` ahead of everything else) — direct invocation of `C:\msys64\mingw64\bin\g++.exe` from a foreign shell silently fails with no output.

`scripts/build-client-rl.sh` encodes all of this (checks `-dumpmachine`, warns if wrong) and is the canonical way to build this client — use it rather than re-deriving the g++ command line.

## How to build and run

```sh
# from a shell where g++ -dumpmachine reports x86_64-w64-mingw32 —
# e.g. /c/msys64/usr/bin/bash.exe --login -c "cd /path/to/repo && ..."
pwsh ./scripts/update-dependencies.ps1   # fetches external/raylib (and ygopro-core) if missing
./scripts/build-client-rl.sh             # builds raylib (first time only) + goat-client-rl
./build/goat-client-rl.exe
```

The script copies the four runtime DLLs it needs (`libgcc_s_seh-1.dll`, `libwinpthread-1.dll`, `libsqlite3-0.dll`, `libstdc++-6.dll`) beside the executable automatically.

## What's built in `src/client_rl/main.cpp` so far

- **Text**: `draw_text(font, text, rect, fontSize, color, style)` — hand-rolled word-wrap (`wrap_text`, greedy line-packing, respects literal `\n`), single-line ellipsis truncation (`truncate_ellipsis`), horizontal (`Left`/`Center`) and vertical (`Top`/`Center`) alignment. This replaces what GDI's `DrawText(DT_CENTER|DT_VCENTER|DT_WORDBREAK|DT_SINGLELINE|DT_END_ELLIPSIS)` gave the Win32 client for free — raylib's `DrawTextEx` only places one string at one point with no wrapping or alignment at all. **Every future screen depends on this being correct.**
- **Drawing primitives**: `draw_panel` (filled rect + outline), `draw_button`/`button` (see above), `draw_bitmap_fit` (letterbox/contain, for card and pack art), `draw_bitmap_cover` (crop/fill, for full-bleed backgrounds like the title screen) — all via `DrawRectangleRec`/`DrawRectangleLinesEx`/`DrawTexturePro`.
- **Images**: `TextureCache` (path → `Texture2D`, loaded via raylib's `LoadImage`/`LoadTextureFromImage`, which decode JPEG/PNG internally — no WIC equivalent needed).
- **Main loop**: raylib's own `while (!WindowShouldClose())` replaces `WM_TIMER`/`WM_PAINT`/`WM_LBUTTONUP`; `IsMouseButtonReleased(MOUSE_BUTTON_LEFT)` matches the Win32 client's up-click semantics exactly. DPI scale approximated via `GetWindowScaleDPI()`.
- **Screens**: `paint_title` (background image, hero text, intro paragraph, Enter Campaign button — ported faithfully from `src/client/main.cpp`'s `paint_title`/`compute_title_layout`, including replicating its two-independent-cut-sequences quirk for the title text vs. the CTA button placement); `paint_hub` (nav row + a select row — COLLECTION, SHOP, EDIT DECK, PLAY CPU, and TEST DUEL all navigate to the real screens; AUTO DUEL remains a stub that just updates the status line); `paint_collection`; `paint_shop`; `paint_pack_opening` (see the "Bug found" note above for its reveal animation); `paint_deck_editor` (owned-card pool — search, Monster/Spell/Trap filters, per-card "(in deck/owned)" counts, a detail panel, the six shared deck-management buttons; **left-click a pool card to inspect it, right-click to add a copy** respecting ownership caps and the 60/15 main/extra editor limits — deliberately split from the original's single-click-does-both, since that made merely browsing the pool add cards as a side effect); `paint_deck_list` (full-screen Main/Extra panels via `ColumnListLayout`, click a row to remove one copy, the same six buttons); `paint_cpu_select` (paged, tier-locked NPC roster shared by PLAY CPU and TEST DUEL, leading to a real duel); `paint_duel` (the duel board — see its own section below). All ported from the equivalent `src/client/main.cpp` functions, reading real data from `goat::game::Progression`/`goat::CardDatabase`/`goat::game::Catalog`/`goat::game::DeckBuilder`/`goat::Banlist`, none of which needed any changes to link into this target since they were already platform-independent.
- **Card grid pattern**: `CardGridLayout`/`compute_card_grid_layout` (Collection, Shop, Pack Opening, the Deck Editor's pool) and `ColumnListLayout`/`compute_column_list_layout` (the Deck List's Main/Extra panels) — both ported from the Win32 client's shared layout helpers, pure `Rect`/`UiScale` math.
- **Deck save/load**: `deck_action_buttons` — Save/Cancel, Save As/Confirm, Load (cycles `decks/player/*.ydk`), Set Active, Back — ported from `src/client/main.cpp`'s `handle_deck_action_buttons` and shared between the Deck Editor and Deck List screens exactly like the original. One fix along the way: that original only ever *positions* its shared native text-entry control on the Collection and Deck Editor screens, so Save As is actually unreachable from its Deck List screen (nowhere visible to type the name). `compute_deck_list_layout` now reserves a `name_box` so this client's Deck List can show the naming field directly instead of reproducing that dead end.
- **Working directory**: `main()` calls `fs::current_path(project_root())` before constructing `AppState`, mirroring `src/client/main.cpp`'s own startup step — every asset/data path in this file (`external/...`, `data/...`, `decks/...`, `saves/...`) is relative to the repo root, not wherever the exe happens to be launched from.
- **Text input**: `text_field(font, rect, text&, active&, scale, mouse, clicked)` — a generic hand-rolled text field via raylib's `GetCharPressed()`/`CodepointToUTF8()`/`IsKeyPressed(KEY_BACKSPACE)`, replacing the Win32 client's native `EDIT` control. Used by Collection's search box, and reused (not extended — see "Remaining phases" #2, done) by the Deck Editor's search/name-entry swap and the Deck List's own name field.
- **The duel board** (`paint_duel`) — the last and largest screen, ported from `src/client/main.cpp`'s `paint_duel`/`handle_duel_click`/`compute_duel_layout` and everything they call:
  - **Layout**: `compute_duel_layout` lays out the inspector, both HUD bars, the turn indicator, the prompt panel, both hand rows, and each side's 5 monster + 6 spell/trap zones (index 5 = Field Spell) plus Deck/Extra/Grave/Banish piles — point-symmetrically mirrored between the two sides (see the function's own comment for exactly which pairs swap and which deliberately don't).
  - **Board state**: `FieldCard`/`LegalAction`/`ActionLayout` structs, `build_action_layout` (maps the engine's flat `legal_actions` list onto zone glow, attack targets, hand-card popups, phase buttons, and a fallback text panel), `compute_duel_hover`/`resolve_board_selection` (what the inspector shows: an explicit zone selection beats hover, hover beats the last-inspected sticky fallback).
  - **Click handling**: `resolve_duel_click` is the one screen in this file that doesn't decompose into independent `button()` calls — Win32's `handle_duel_click` has ~9 ordered, mutually-exclusive priority branches (inspector action buttons → hand popup → hand cards → phase buttons → all-zone-placement mode → attacks → zone selection → prompt panel/pager), so this is one dedicated function mirroring that exact order, called once per frame before drawing rather than folded into the draw calls. See its own doc-comment for why.
  - **Life-total animation**: framerate-independent by construction — `life_display[i] += (life[i] - life_display[i]) * (1 - pow(1 - 0.2, dt/0.15))` reaches the same ~20%-per-150ms decay the Win32 client's fixed-interval `WM_TIMER` version does, regardless of actual frame time, rather than porting the flat per-tick lerp as-is (which would run 4x too fast at 60fps).
  - **Polling cadence**: `poll_player_duel`/`poll_board_snapshot` are throttled to a 150ms interval (`kPollIntervalSeconds`), matching the Win32 client's own WM_TIMER cadence — an earlier version of this polled every frame (~9x more filesystem opens/sec) before that was identified as amplifying real IPC contention; see "Bugs fixed" above.
  - **`draw_bitmap_rotated`** — the raylib replacement for the Win32 client's `PlgBlt`-based defense-position card rotation, via `DrawTexturePro` with a swapped-dimension pre-rotation box and a 90° rotation around its center.
  - **Simplification**: `hand_action_short_label` and `short_action_label` (two near-identical verb-stripping tables in the original, one for the hand popup and one for the inspector's board-selection buttons) are unified into one `short_action_label`, since the inspector's table there was already a strict superset.
- **Engine IPC** (`start_player_duel`, `poll_player_duel`, `poll_board_snapshot`, `submit_action`, `run_automatic_duel`) — the file-based `request.txt`/`response.txt`/`state.txt`/`result.txt` protocol itself needed zero changes (it's already plain `std::filesystem`); only the process-spawning underneath it needed a cross-platform abstraction, which is `ProcessBridge` (see the file map above) — a `spawn`/`poll`/`terminate`/`close_handles`/`run_and_capture` API with a `CreateProcessW`-based Windows implementation and a `fork()`+`execve()`-based POSIX one (not `posix_spawn()`'s `_np` chdir extension — see `ProcessBridge.cpp`'s own comment; that extension is a non-portable glibc/BSD addition this Windows-only dev environment could never verify against a real macOS runner, so it was avoided in favor of plain, universally-available POSIX primitives) behind `#ifdef _WIN32`. `submit_action`'s atomic temp-file-then-rename write (with a retry-on-failure added after a real hang was diagnosed) is preserved; `poll_player_duel`'s freshness check was rewritten entirely — see "Bugs fixed" above for why `fs::last_write_time` doesn't drive it anymore.
- **Font**: raylib's built-in default font (`GetFontDefault()`). No bundled TTF yet — see "Visual polish" below.

## Verification approach

Build via `scripts/build-client-rl.sh`, then confirm the process starts and stays running (e.g. launch it, wait a couple seconds, check the process is still alive, then close it) rather than clicking through the UI interactively — that's been the standing preference in this project throughout, and it still holds: interactive testing is left to whoever's driving.

**Re-confirmed now that the duel board exists, as flagged for this exact point:** launch-and-stay-alive is still the bar for "doesn't crash," but it doesn't touch any duel-board code path at all (nothing spawns `goat-sim` until a duel is actually started), so it says nothing about whether a duel actually plays correctly. For this phase specifically, verification also included a standalone program that called `ProcessBridge::spawn` with the exact same arguments `start_player_duel` builds (same `--decision-dir`, `--human-player 1`, etc.) against the real `goat-sim.exe`, and confirmed both that the process starts and that `request.txt` appears with the expected `title\nindex|label` format within a few hundred ms. That validates the IPC plumbing end-to-end but is not the same as playing a duel — the click-priority logic in `resolve_duel_click`, the zone-glow legality rules, and the hand-popup/inspector interactions have only been read against the Win32 original for fidelity, not exercised against a live duel. Treat the duel board as "should work, built carefully, not yet proven" until someone actually plays one through.
